# Portability census of VacuumTube 2.0.0's preload tree

> Sanitised copy of the census produced while reverse engineering the shipped `resources/app.asar`
> (local absolute paths replaced). It records, for every one of the 74 files under `src/preload/`:
> what it patches and when, the Electron/Node APIs it needs, the config keys it reads, and a
> portability verdict for a plain Chromium/Android-WebView page context. Line references are to the
> unmodified extracted files, which are mirrored in `vendor/vacuumtube-preload/`.
# VacuumTube 2.0.0 â€” `src/preload` census (for an Android WebView port)

Target: `<extracted app.asar>\src\` (extracted `app.asar`, VacuumTube 2.0.0, an Electron wrapper of YouTube Leanback `https://www.youtube.com/tv`).
Method: every one of the 74 files under `src\preload\` (70 `.js` + 4 `.css`) was read, plus `src\index.js` (main), `src\config.js`, `src\constants.js`, `src\ua.js`, and handler greps in `src\permissions.js` / `src\userstyles.js` / `src\updater.js`. Line references are to the extracted files. Read-only: the only file created is this document.

Preload is loaded by `BrowserWindow` with `nodeIntegration:false`, `contextIsolation:false`, `sandbox:false`, `nodeIntegrationInSubFrames:true` (`src\index.js:355-362`). So **preload code runs in the page's main JS world with full Node access, at document-start, in the top frame *and* every subframe**. That combination is the single biggest assumption of this codebase.

Verdict legend:
- **as-is** = reusable as-is in a plain Chromium/Android-WebView page context (page APIs + injected DOM only).
- **shim: X** = reusable with shim `X` (named bridge/replacement needed).
- **native** = needs native Android replacement (cannot be meaningfully done from page JS).

## 2. Module load order and wiring

### 2.1 `src/preload/index.js` (the whole wiring)

```
if (location.host === 'www.youtube.com' && location.pathname === '/tv') {   // index.js:1
    const xhrModifiers = require('./util/xhrModifiers')                    // :2  â†’ patches window.XMLHttpRequest NOW
    xhrModifiers.block()                                                   // :3  â†’ defers all send() until unblock()
    const fs = require('fs'); const path = require('path')                 // :5-6
    let moduleFiles = fs.readdirSync(path.join(__dirname,'modules'), {withFileTypes:true}) // :8-9
    ... push(require(modulePath))   // dirs â†’ <name>/index.js, *.js files â†’ file   :12-23
    for (let module of modules) { try { module() } catch (err) { console.error(...) } }  // :25-31
    xhrModifiers.unblock()                                                 // :33
}
```

Facts that matter for a port:

1. **Require order == readdir order**, and it is *not* sorted by the code. Observed by listing: `adblock, block-continue-watching, block-sign-in-popup, cast-label, controller-support, css, dearrow, disable-direct-sign-in, encryption-notice, fix-exit, fix-reloads, fix-voice, guide-tabs, h264ify, hide-shorts, keybinds, leanback-settings, low-memory-mode, media-capabilities, mouse, no-f11, pause-on-blur, remaining-time, remove-super-resolution, return-youtube-dislike, sponsorblock, support-webp, touch-support, ultrawide, userstyles, voice-privacy-notice` for files, and the directory entries (`h5vcc`, `music-mode`, `settings`, `speed-control`, `volume-control`) interleave alphabetically. `fs.readdirSync` order is filesystem-defined (NTFS tends to be alphabetical; Linux is directory order) â€” the design deliberately tolerates this because module bodies register hooks rather than depending on each other's output.
2. **Two distinct phases per module**: (a) *require-time* top-level code (shared util initialisation, `configManager.get()` capture, XHR/JSON/environment patching, `os.hostname()`, `fs.readFileSync` of CSS, `process.platform` reads, static `ipcRenderer` subscriptions) and (b) *call-time* code inside the exported function (registrations that need a live config/locale, DOM building, intervals, extra `ipcRenderer.on` handlers). Failures in phase (b) are swallowed per module (`:28-30`); failures in phase (a) abort the whole loop and the remaining modules are never invoked.
3. **`xhrModifiers.block()/unblock()`** is the only cross-module sequencing mechanism: Leanback fires an Innertube XHR immediately on load, so all `send()` calls are queued until every module has registered its response modifier.
4. Every module receives **no arguments** and returns nothing (one exception class: pages export objects). All coupling is through the shared `require` cache of `util/*` singletons (`jsonModifiers`, `xhrModifiers`, `configOverrides`, `resolveCommandModifiers`, `controller`, `css`, `localeProvider`).
5. `window.h5vcc`, `window.vtOpenSettingsOverlay`, `window.vtToggleSettingsOverlay` are the page-visible API VacuumTube adds; `window.vt*` + `vt-userstyle-toggle` CustomEvent are also used *internally* (leanback-settings â†’ settings overlay).

### 2.2 `src/preload/config.js` and the main-process side

* Preload: `ipcRenderer.sendSync('get-config')` at require time (`config.js:3`) returns the main process's live config object; `sharedConfig` is a shallow copy. `config-update` (`config.js:6-9`) **empties and repopulates `sharedConfig` in place**, which is why `const config = configManager.get()` captured at module require time stays current.
* `set(newConfig)` uses **`sendSync('set-config')`** (`config.js:16`) and replaces `sharedConfig` contents with what the main process returns. Comment: "hate to use sendSync since it's blocking, but i have no choice since youtube doesn't await stuff on ui calls".
* Main: `ipcMain.on('get-config')` returns `config` (`src/index.js:244-246`); `ipcMain.on('set-config')` â†’ `configManager.update(newConfig)` (merges `{...defaults, ...config, ...newConfig}`, `src/config.js:152-160`) â†’ `configManager.get()` â†’ `win.webContents.send('config-update', config)` (`src/index.js:248-261`) â†’ `updater.onPreferenceChanged()` when `auto_update` is present.
* Main also pushes `config-update` on fullscreen enter/leave when not forced (`src/index.js:427-441`). Persistence is debounced: `setInterval(save, 500)` + atomic temp-file rename (`src/config.js:111-150`).
* **Enable/disable model: there is none at the module level.** All 70 JS files under `preload/modules` are always required and always invoked. Each behavior gates itself at request/call time by reading config (e.g. `if (!config.adblock) return;`). The only "dependency" mechanism is `dependsOn` in the settings schema (UI greying only) and `features_enabled` gating `music_mode_feature` / `remaining_time_feature` / `ultrawide_feature`.

## 6. Highest-risk items for an Android WebView port (ranked)

1. **Node module system inside preload** â€” `preload/index.js:5-23` uses `fs.readdirSync` + dynamic `require(absolutePath)` for 70 files, and 15+ modules use `fs.readFileSync`/`path.join(__dirname, â€¦)` to load their own CSS/locale/icon assets (`modules/css.js:7`, `speed-control/index.js:15`, `volume-control/index.js:16`, `settings/index.js:169`, `settings/pages/about.js:8`, `util/localeProvider.js:42`). In a WebView there is no `fs`, no `__dirname`, no `require`. Requires a bundler step (inline every module + asset string) and an injected-script loader, and the "load 70 modules, catch failures individually" resilience must be reproduced deliberately.
2. **Main-world injection + `contextIsolation`** â€” the whole design assumes preload runs in the page's JS world (`src/index.js:357 contextIsolation:false`). Android `WebView.addJavascriptInterface` lives in a *different* world and is only reachable from page JS as an object; the patches in Â§5 (`JSON.parse`, `XMLHttpRequest`, `_yttv.resolveCommand`, `window.h5vcc`â€¦ ) are invisible unless a `WebViewCompat.addDocumentStartJavaScript`/`evaluateJavascript` runs in the page world **before** Leanback loads. Mistake here silently disables approx. 80 % of the feature set.
3. **Blocking config IPC (`sendSync`)** â€” `preload/config.js:3,16` and `settings/schema.js:45`. Android JS bridges are asynchronous; `set()` is called from synchronous UI/command paths (`render.js:59`, `music-mode/index.js:75`, `volume-control/index.js:69`, `guide-tabs` row `set`). Needs either a synchronous `@JavascriptInterface` returning a JSON string (works, but blocks the WebView thread) or a local optimistic config object plus async persistence (behaviour change: read-back values lag).
4. **DIAL/SSDP stack** â€” `modules/h5vcc/dial/*` needs `dgram` UDP multicast on port 1900, an `http` server on `0.0.0.0:0`, `os.networkInterfaces()`, `crypto.randomUUID()`, `Buffer.concat` (`:107`), and `Headers`/`DOMParser`/`XMLSerializer`. Nothing here can run in a page. Android replacement: `MulticastSocket`/`NsdManager` + a native HTTP server, exposed to the page as a JS object shaped like `window.h5vcc.dial.DialServer` (`h5vcc/index.js:88`, `dial/server.js:112-144`). `device_discoverability` must also be honoured.
5. **User-agent and client-hint spoofing** â€” Leanback gates the TV surface on a TV/console UA; the main process sets a Cobalt 27 PS4-style UA at request level *and* `sec-ch-ua*` headers, plus `Emulation.setUserAgentOverride` with `userAgentMetadata` for the page and every iframe (`src/ua.js:63-109,113-141`; `src/index.js:235-241,421-424`). Android WebView can set `setUserAgentString` but cannot rewrite `sec-ch-ua*` per request and has no `webContents.debugger`, so client-hint mismatch (`navigator.userAgentData` vs UA) is likely â€” YouTube may serve the wrong player build, disable HDR/HFR, or break bot checks.
6. **CSP modification** â€” the main process rewrites `Content-Security-Policy` (removes Trusted-Types, adds `style-src 'unsafe-inline' data: *`, `connect-src sponsor.ajay.app returnyoutubedislikeapi.com data:`, `img-src dearrow-thumb.ajay.app data:`, `font-src * data:`) and cancels `csp.withgoogle.com` (`src/index.js:157-233`). Android WebView exposes no response-header callback; the equivalent is `WebViewClient.shouldInterceptRequest` re-fetching and rewriting the header, or losing `<style>` injection, SponsorBlock, DeArrow and RYD.
7. **`process.*` used at module top level** â€” `modules/cast-label.js:5` (`process.platform`) and `modules/h5vcc/dial/constants.js:8` run at require time; with `process` undefined they throw, and because `preload/index.js` requires modules *before* invoking them, a throw there aborts the loader loop for the remaining modules. Also `voice-privacy-notice.js:6`, `fix-voice.js:36,85`, `settings/schema.js:72,118` (`process.platform`), `settings/pages/about.js:16-17` (`process.platform`, `process.arch`). Needs a `process` shim (`{platform:'android', arch:'arm64'}`) â€” and platform-conditional branches then silently change behaviour (e.g. the mac mic guard never installs, the mac-permissions page is hidden, `wayland_hdr` is hidden).
8. **Frame coverage** â€” `nodeIntegrationInSubFrames:true` (`src/index.js:359`) exists because "youtube may place the entirety of leanback in a frame". Android `evaluateJavascript`/document-start injection applies to the **main frame only**; child-frame injection requires `WebViewCompat.addDocumentStartJavaScript` with matching rules (or a custom `WebViewClient` per frame). Without it, the whole feature set disappears in the iframe case.
9. **Native window/app lifecycle glue** â€” `fix-exit.js:12` uses `window.close()` (no-op for a WebView's main frame), `fix-reloads.js:10` asks the main process to reload (a plain `location.reload()` would drop the injected script), `pause-on-blur.js:20` needs `onPause`/`onWindowFocusChanged` events, `util/controller.js:39-45` needs the same focus/blur stream. All three need an injected event source, and the two commands need a native `finish()`/`reload()` bridge.
10. **Fixed-device media assumptions** â€” `media-capabilities.js:6-19` hard-codes a TV/Cobalt capability envelope (8K width/height, 60 fps, 200 Mbps, 8 channels, HDR only when `matchMedia('(dynamic-range: high)')` matches) and `h5vcc/index.js:9-18,95` derives/overrides the video container size (`'7680x4320'` when `unlock_resolution`). On Android the values that matter are the real decoder/panel capabilities; declaring 8 K can push Leanback into formats the device cannot play (`window.screen` is also in CSS px, not device px, so the fallback resolution is wrong on high-DPI screens).
11. **Hard-coded third-party endpoints + timers** â€” `sponsor.ajay.app` (`sponsorblock.js:29`, `dearrow.js:15`), `returnyoutubedislikeapi.com` (`return-youtube-dislike.js:11`), both via page `fetch` with `AbortSignal.timeout(2000)`, plus in-memory caches and 1 s/250 ms/100 ms/20 ms polling intervals. These need network permission (already granted to a WebView) plus the CSP work of risk 6; the DNS/TLS paths also need a UA that third parties accept.
12. **Clipboard** â€” `keybinds.js:70` calls `navigator.clipboard.writeText`. In Android WebView this can reject without a user gesture (`NotAllowedError`) â€” a keydown handler may or may not count â€” so a `ClipboardManager` bridge is the safe route.
13. **Userstyles and locale file I/O** â€” `modules/userstyles.js:37,99` + `settings/pages/userstyles.js:6` expect `get-userstyles`/`open-userstyles-folder`/`userstyle-updated`/`userstyle-removed` from the main process watching a real folder (`src/userstyles.js:58-123`); `util/localeProvider.js:42-55` reads `locale/*.json` from disk. Both must become bundled assets or a native asset/SAF bridge.
14. **Updater/about surface** â€” `settings/pages/about.js:23,80-88,105,133-134` is entirely built on the Electron updater (`src/updater.js:80,206-216`). On Android this is Play/APK self-update; the page needs re-implementation or removal.
15. **Microphone** â€” `fix-voice.js:26-33` and `settings/pages/mac-permissions.js:33-66` depend on `request-microphone-permission`/`get-â€¦`/`reset-â€¦`/`open-â€¦-settings` IPC (`src/permissions.js:141-153`). Android needs `WebChromeClient.onPermissionRequest` + runtime `RECORD_AUDIO` handling, and the macOS-only guard (`fix-voice.js:36`) should be ported as the Android permission gate if voice search must work.
16. **Gamepad/controller support** â€” `util/controller.js:47-69` polls `navigator.getGamepads()` every frame, hard-codes a Steam Input device-id suffix (`:59`) and maps buttons to keycodes 32768+; `controller-support.js:35-55` then synthesises `keydown`/`keyup` `Event`s. Android WebView gamepad support is version/OS dependent and cannot see keys, so controller support likely needs native `onKeyDown`/`onGenericMotion` â†’ injected key events.
17. **Config-write churn from the volume interval** â€” `volume-control/index.js:146-148` calls `setVolume(true)` every 100 ms, and `setVolume` persists via the blocking `sendSync('set-config')` whenever the value changed (`:67-70`). With an async or slow Android bridge this is a plausible ANR/jank source; the interval should be restructured.
18. **Misc native abilities relied on indirectly** â€” `shell.openExternal` (`settings/index.js:58`, plus `leanback-settings.js:144` commented), `relaunch-app` (`mac-permissions.js:66`), `os.hostname()` for the cast label (`cast-label.js:4`), `crypto.randomUUID()` (`dial/constants.js:5`), `package.json` version via `require` (`dial/constants.js:3`, `dial/server.js:3`) and the base64 app icon (`settings/pages/about.js:8`). Each maps to a small native call on Android.
19. **Deep links** â€” `h5vcc/index.js:62,84` consumes `get-deeplink`/`deeplink` from the main process (single-instance + `youtu.be` normalisation in `src/index.js:515-544`). Android needs `intent-filter` handling â†’ injected `onDeepLink` events, including the pre-listener queue (`h5vcc/index.js:50-81`).
